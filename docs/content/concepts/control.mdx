---
title: Two control signals
description: raise Stop, and a tool.pre hook that returns a result. There is no third one — everything else is either an answer or an exception.
---

There are exactly two ways to steer the loop from outside it. One is raised,
one is returned. Everything else that happens to a run is either an answer the
model reads or an exception you catch.

## raise Stop

```python
from core import Stop, hook


@hook("model.post")
async def enough(answer) -> None:
    if "goodbye" in answer.text.lower():
        raise Stop
```

Raise it from any hook or any tool. The loop catches it and ends the run
cleanly: no traceback reaches your `await`, and what comes back is the `Run`
holding everything written down so far — the notebook up to that point, the
step count, the pocket. A stop is an ending, not an error.

Two of the [shipped cards](/hooks/cards) are this and nothing more.
`Steps(n)` counts turns off `run.step` and raises. `Budget(max_tokens)` adds up
what each reply cost and raises past the limit — and appends that last reply to
the notebook itself first, because the loop's own append is one of the things a
`Stop` skips. If you stop mid-stage, know what the stage had not done yet.

`run.post` always fires. It is a `finally`, so it runs after a clean finish,
after a `Stop` and after a crash. Two consequences:

- A `Stop` raised inside a `run.post` hook is ignored — too late to stop
  anything.
- Any other exception out of `run.post` propagates the ordinary way, with
  whatever was already in flight attached as its `__context__`.

## Return a result from tool.pre

The second signal is not raised, it is returned:

```python
from core import ToolCall, hook


@hook("tool.pre")
async def guard(call: ToolCall):
    if call.name == "rm":
        return "denied: ask a human first"     # the tool never runs
```

| you return | what the loop does |
| --- | --- |
| `None` | nothing — the call goes through as it is |
| a `ToolCall` | runs that one instead: a reroute, or the same call with better arguments |
| a `str` | skips the tool; this *is* its result, written into the notebook for the model to read |
| a `Message` | the same, when the result needs parts rather than plain text |

A result also ends the ring: the first card that answers with one wins, and the
cards behind it never hear that bell. That is the whole deny path — no third
signal, no boolean to return. `Permission(deny, allow, ask)` is this signal
wearing a uniform, and its refusals are ordinary strings like
`denied: rm`.

## What is not a signal

A tool that raises is not a control signal. The loop catches the exception,
writes it into the notebook as that call's result, and the model gets another
turn:

| what happened | what the model reads |
| --- | --- |
| the tool raised | `error: ValueError: nope` |
| it asked for a tool that is not in the toolbox | `error: unknown tool: ghost` |
| the provider could not parse the call's arguments | `error: tool arguments were not valid JSON: …` |

Run-time mistakes are answers, not crashes: the model reads its own mistake and
tries again, which is usually what you wanted. The loop catches exactly two
things — a `Stop`, and a tool's own exception. Everything else propagates: a
model that raises, a hook that raises, and `ContractError` first among them,
because a wiring mistake is not something a model can fix by trying again.

<Warning>
  A `Stop` from a tool inside a parallel batch waits for the batch. Every call
  in it runs to the end — nothing is cancelled mid-write, so no half-written
  file is left behind — and the `Stop` is raised once they are all done, first
  in call order. The results ahead of it are already in the notebook; the ones
  behind it are dropped, though their tools did run. See
  [parallel tools](/tools/parallel).
</Warning>
