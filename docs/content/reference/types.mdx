Three plain dataclasses, in `core/types.py`. Every other part of stellar talks
in these three, and nothing here imports the rest of core.

`dataclasses.asdict` turns one into a dict you can save. Building it back is
your job, including the `ToolCall`s and `Part`s inside a `Message`.

## Part

```python
from core import Part

Part(type, data=None)
```

One piece of a message. `type` names the piece and `data` holds it. A model
that streams sends its reply as a series of `Part`s.

<ResponseField name="type" type="str" required>
  Which piece this is. `fold()` and the adapters read this word.
</ResponseField>

<ResponseField name="data" type="Any" default="None">
  The payload. Its shape is whatever `type` promises.
</ResponseField>

Core handles three types itself when it joins parts into a message:

| type | data | what core does with it |
| --- | --- | --- |
| `text` | `str` | text next to more text joins into one part |
| `tool_call` | `ToolCall` | added whole to `message.tool_calls`, and anything else raises `ContractError` |
| `meta` | `dict` | merged into `message.meta`, later keys winning |

One more type is spelled the same way everywhere, so adapters agree. An `image`
part carries `{"url": …}` or `{"media_type": …, "data": <base64 str>}`.

Every other type belongs to an adapter and lands in `content` untouched. That is
where thinking blocks and provider extras go.

## ToolCall

```python
from core import ToolCall

ToolCall(id, name, args={})
```

The model asking for one tool to run. The loop turns each one into a tool
message.

<ResponseField name="id" type="str" required>
  The provider's id for this ask. The tool message answers it in
  `Message.tool_call_id`.
</ResponseField>

<ResponseField name="name" type="str" required>
  Which tool to run. It is the key the tool is filed under in `agent.tools`.
</ResponseField>

<ResponseField name="args" type="dict[str, Any]" default="{}">
  The call's keyword arguments, already parsed. A fresh dict per call. The loop
  spreads it as `execute(run, **args)`.
</ResponseField>

<Note>
  Core reads one convention it never writes. An adapter that could not parse a
  call's arguments hands back empty `args`. It puts the raw string in the
  assistant message's `meta["invalid_args"][id]`. The loop makes that the tool's
  result, `error: tool arguments were not valid JSON: ...`. The model reads its
  own mistake instead of a `TypeError`.
</Note>

## Message

```python
from core import Message

Message(role, content="", tool_calls=[], tool_call_id=None, meta={})
```

One line in the conversation. A list of these is what your agent sends, and
what comes back.

<ResponseField name="role" type='"system" | "user" | "assistant" | "tool"' required>
  Who the line is from.
</ResponseField>

<ResponseField name="content" type="str | list[Part]" default='""'>
  The parts. Always `list[Part]` once the message is built.
</ResponseField>

<ResponseField name="tool_calls" type="list[ToolCall]" default="[]">
  Assistant messages only. A fresh list per message.
</ResponseField>

<ResponseField name="tool_call_id" type="str | None" default="None">
  Tool messages only. It is the `ToolCall.id` this message answers.
</ResponseField>

<ResponseField name="meta" type="dict[str, Any]" default="{}">
  Anything the provider sent along. Adapters put usage here as
  `{"usage": {"input_tokens": …, "output_tokens": …}}`, which is what `Budget`
  reads, and `meta["model"]` names who answered.
</ResponseField>

### A string becomes one text part

You can pass a plain string as `content`. It becomes one text part while the
message is built, and the empty string becomes an empty list.

```python run
from core import Message

print(Message("user", "hi").content)
print(Message("assistant").content)
```

```text output
[Part(type='text', data='hi')]
[]
```

So there is one shape to read everywhere, and one shape to load back from a
checkpoint.

### Message.text

```python
from core import Message

@property
def text(self) -> str: ...
```

Every text part, joined. Other parts are skipped, so `run.messages[-1].text` is
the answer even when the reply also carried pictures or thinking.

<ResponseField name="text" type="str">
  The `data` of every `Part` whose type is `text`, joined in order.
</ResponseField>
