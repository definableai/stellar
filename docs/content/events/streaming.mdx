---
title: Read events as they happen
description: stream() hands you one job's events, one at a time, from the start and then live.
---

`stream()` gives you one job's [events](/events/overview), in order, one at a
time. It replays what already happened, then stays open and hands you each new
event as it lands. When the job ends, the stream ends.

Use it when your reader has to wait for something, like a web handler or a
queue. A plain listener cannot, because it is never `async def`.

## Try it

Start the job as a task so the stream can read it while it runs. Keep the
task. It is where the `Run`, and any error, comes back.

```python run
import asyncio

from core import Agent, FakeModel, Message, ToolCall, tool


@tool
async def shout(word: str) -> str:
    """Shout a word."""
    return word.upper()


async def main() -> None:
    agent = Agent(FakeModel([
        Message("assistant", "", [ToolCall("c1", "shout", {"word": "hi"})]),
        Message("assistant", "done"),
    ]), [shout])
    job = asyncio.create_task(agent.run("shout hi", run_id="a"))
    async for event in agent.events.stream(run_id="a"):
        print(event.seq, event.name)
    await job


asyncio.run(main())
```

```text output
0 run.pre
1 model.pre
2 model.delta
3 model.post
4 tool.pre
5 tool.post
6 model.pre
7 model.delta
8 model.post
9 run.post
```

- `run_id="a"` names the job up front. The reader knows what to ask for
  before there is anything to read.
- The `async for` ended on its own, at `run.post`.
- `stream()` takes the same two filters as `listen`: `run_id` picks one job,
  `prefix` picks a family of names.

## The stream always ends

The loop writes `run.post` at the very end, whether the job finished, was
stopped, or raised. That is what closes the stream, so a reader never hangs.
It closes on `run.post` even when a `prefix` hid every other event.

A stream with no `run_id` watches the whole agent, and that one has no ending.
You leave it when you are done.

## Reconnecting costs nothing

Open the stream before the job, halfway through, or after it has finished. You
get the same events in the same order every time, because the replay fills in
whatever you missed.

`since=4` starts the replay at that `seq` instead of the beginning. It only
trims the replay, so a bookmark past the end still hears everything that comes
next.

## Limits

- Nothing caps the event log, or the queue behind a stream. A long-lived agent
  uses more and more memory, and a reader slower than the loop builds up a
  backlog. Cap them yourself when that starts to matter.
- Leaving a stream early with `break` does not tidy it up. Give the stream a
  name and `await` its `aclose()` if you stop reading before the job ends.
