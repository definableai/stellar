---
title: Concurrent runs
description: One agent can run a hundred conversations side by side. Here is what they share.
---

An [`Agent`](/reference/agent) holds no conversation of its own. The messages,
the step count and `extra` all live on the `Run`. So a hundred people is one
line of `asyncio`.

## Example

Give each job a name with `run_id=` and you can tell them apart in the log.
The name is fixed before the job starts, which is what lets a reader
[watch one](/events/streaming) while it happens.

```python run
import asyncio

from core import Agent, FakeModel


async def main() -> None:
    agent = Agent(FakeModel(["sun", "moon", "stars"]))
    agent.events.listen(lambda event: print(event.run_id, event.name), "run")

    done = await asyncio.gather(
        agent.run("one", run_id="a"),
        agent.run("two", run_id="b"),
        agent.run("three", run_id="c"),
    )
    print([job.messages[-1].text for job in done])


asyncio.run(main())
```

```text output
a run.pre
a run.post
b run.pre
b run.post
c run.pre
c run.post
['sun', 'moon', 'stars']
```

The three jobs share one event log and one numbering. Filter on the way in,
with `listen(fn, run_id=rid)` or `stream(run_id=rid)`, rather than sorting the
whole thing out afterwards.

<Note>
  Those three finished in order because [`FakeModel`](/models/testing) never
  waits for anything. Each job ran to the end before the next one started. Put
  a real model behind it and the network is the waiting point. The three jobs
  overlap, and the lines above arrive mixed together.
</Note>

## Shared state

- the model, the toolbox and the agent's hooks
- `agent.extra` and the event log

Nothing in core takes a lock. Those last two are the only places one job can
write where another will see it. Keeping them tidy is yours.

## Per-run state

- `run.messages`, `run.step` and `run.extra`
- `run.hooks`, this job's own rules, which run after the agent's

Neither one is an argument to `agent.run`. You reach them from inside the job,
through the `run` that every hook and every tool is handed.

## Hot-swapping components

Swapping a part is an assignment, and the agent checks all its parts again at
the top of every step. So you can change the model mid-flight. The next job to
take a step either uses it or raises `ContractError` naming what to type
instead. `agent.hooks.attach(rule)` reaches every job already running, at its
next stage of that kind.

<Warning>
  Use `attach` and `detach`, not `agent.hooks = something`. A job ties itself
  to the agent's hooks the moment it is born. Replace them wholesale and every
  job already running stays on the old set.
</Warning>

<Note>
  One agent means one event log, and nothing prunes it. With many jobs sharing
  one agent for a long time, that is the limit you will run into first.
</Note>
